## 一、全局约定（沿用第一阶段，再强调一次）

### 1.1 统一返回格式

所有接口，无论成功失败，都返回这个形状：

```json
{ "code": 0, "msg": "成功", "data": {} }
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | int | `0` = 成功，非 0 = 失败（具体看错误码表） |
| `msg` | string | 给人看的提示，**前端直接弹出来**就行 |
| `data` | object / array / null | 成功时的数据，失败时为 `null` |

### 1.2 鉴权方式

除 `GET /api/questions` 外，**其余 5 个接口都必须登录**。前端在请求头里带：

```
Authorization: Bearer <token>
```

后端行为：

- token 缺失 / 无效 / 过期 → 返回 `code: 401`，`msg: "请先登录"`
- **不要相信前端传的 user_id**，后端一律从 token 反查用户。这是安全底线（第一阶段已经踩过这个点）

### 1.3 字段命名

- 一律**小写 + 下划线**：`user_id`、`case_id`、`school_level`（禁止 `userId`、`caseId`）
- JSON 字段值里的中文**原样存原样返回**，后端不做转义

### 1.4 新增错误码

在第一阶段 1001-1004 之后继续编号：

| code | 含义 | 谁触发 | 前端怎么处理 |
|------|------|--------|-------------|
| 1005 | 问卷未填写 | 用户没填问卷就去查答案 / 用对话 | 引导跳转到问卷页 |
| 1006 | 问卷格式不对（选项值不在允许范围内） | 提交问卷时 | 提示用户重新选 |
| 1007 | 提问太频繁（超过每日次数上限） | 调用对话接口 | 提示"今日次数已用完，明天再来" |
| 2001 | 大模型服务异常 | 调用模型失败 / 超时 | 提示"AI 暂时不可用，请稍后再试" |

> 原有码：`1001` 参数格式不对、`1002` 密码太短、`1003` 用户名已存在、`1004` 用户名或密码错误、`401` 未登录、`5000` 服务器内部错误。

## 三、接口详情

### 3.1 GET `/api/questions` —— 获取问卷题目

**作用**：前端问卷页一次性拿到所有题目，按 `group_name` 分三组渲染。

**请求**：无参数，无需登录。

**返回**：

```json
{
  "code": 0,
  "msg": "成功",
  "data": {
    "list": [
      {
        "id": 1,
        "group_name": "direction",
        "content": "你毕业后想去哪？",
        "q_type": "single",
        "options": ["考研", "就业", "考公", "留学", "创业", "还没想好"],
        "order_no": 1
      },
      {
        "id": 4,
        "group_name": "status",
        "content": "当前年级",
        "q_type": "single",
        "options": ["大一", "大二", "大三", "大四", "研究生"],
        "order_no": 4
      },
      {
        "id": 10,
        "group_name": "interest",
        "content": "补充说明",
        "q_type": "text",
        "options": [],
        "order_no": 10
      }
    ]
  }
}
```

**字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | int | 题目 ID |
| `group_name` | string | 分组：`direction`（方向）/ `status`（现状）/ `interest`（想了解） |
| `content` | string | 题干 |
| `q_type` | string | `single` 单选 / `multi` 多选 / `text` 填空 |
| `options` | array | 选项列表，**后端已经把数据库里的 JSON 字符串解析成数组了**；`text` 类型返回空数组 |
| `order_no` | int | 排序号，前端按它排 |

**重要**：`options` 必须是**数组**而不是字符串。后端从数据库读出来是 `'["考研","就业"]'` 这种字符串，**必须 `json.loads` 之后再返回**，否则前端拿到的是字符串没法渲染。

**排序**：后端按 `order_no` 升序返回，前端直接顺序渲染即可。

### 3.2 POST `/api/answers` —— 提交问卷答案

**作用**：用户填完问卷提交。一个用户只有一份问卷，**重复提交直接覆盖**（不新增记录）。

**请求头**：`Authorization: Bearer <token>`

**请求体**：

```json
{
  "direction": "考研",
  "grade": "大三",
  "status": {
    "major_type": "理工类",
    "school_level": "普通一本",
    "score": "前30%",
    "english": "已过六级",
    "experience": ["实习", "竞赛获奖"]
  },
  "interest": ["具体怎么准备", "时间节点怎么安排"],
  "extra_note": "数学基础比较差"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|:----:|------|
| `direction` | string | ✅ | 主方向，必须是问卷选项之一 |
| `grade` | string | ✅ | 年级 |
| `status` | object | ✅ | B 组现状答案，键值对形式 |
| `interest` | array | ✅ | C 组想了解什么，最多 3 个 |
| `extra_note` | string | ❌ | 补充说明，可以空 |

**成功返回**：

```json
{ "code": 0, "msg": "提交成功", "data": { "id": 1 } }
```

**失败情况**：

| 情况 | 返回 |
|------|------|
| 未登录 | `{ "code": 401, "msg": "请先登录" }` |
| `direction` 为空或不在选项内 | `{ "code": 1006, "msg": "请选择未来方向" }` |
| `grade` 为空 | `{ "code": 1006, "msg": "请选择当前年级" }` |
| `interest` 超过 3 个 | `{ "code": 1006, "msg": "最多选 3 项" }` |

**后端实现要点**：

1. `status` / `interest` 存进数据库时要 `json.dumps(obj, ensure_ascii=False)` 转成字符串
2. `user_id` 从 token 反查，**不接受前端传**
3. `answers.user_id` 上有 UNIQUE 索引，所以用「先查再改，没有就插」的写法：

```python
ans = Answers.query.filter_by(user_id=uid).first()
if ans is None:
    ans = Answers(user_id=uid)
    db.session.add(ans)
ans.direction = direction
ans.grade = grade
ans.status_json = json.dumps(status, ensure_ascii=False)
ans.interest_json = json.dumps(interest, ensure_ascii=False)
ans.extra_note = extra_note
db.session.commit()
return ok({"id": ans.id}, "提交成功")
```

### 3.3 GET `/api/answers` —— 查询我的问卷结果

**作用**：前端进首页时判断"这个用户填过问卷没有"，也用于个人中心的"我的问卷"回显。

**请求头**：`Authorization: Bearer <token>`

**请求参数**：无。

**已填过返回**：

```json
{
  "code": 0,
  "msg": "成功",
  "data": {
    "filled": true,
    "answer": {
      "id": 1,
      "direction": "考研",
      "grade": "大三",
      "status": {
        "major_type": "理工类",
        "school_level": "普通一本",
        "score": "前30%"
      },
      "interest": ["具体怎么准备", "时间节点怎么安排"],
      "extra_note": "数学基础比较差",
      "created_at": "2026-10-01 20:30:00"
    }
  }
}
```

**没填过返回**：

```json
{ "code": 0, "msg": "未填写", "data": { "filled": false, "answer": null } }
```

**关键设计**：**没填过不报错**。用 `filled: false` 表达"还没填"，而不是返回 1005。
因为前端是"进首页时顺手查一下"，用它来决定跳不跳转问卷页——这是一个正常的判断流程，不是错误。

> `1005 问卷未填写` 用在**别的地方**：用户没填问卷就直接调 `/api/chat`（对话需要问卷做上下文），那时候才是错误。

**字段说明**：

| 字段 | 说明 |
|------|------|
| `filled` | true / false，前端拿这个判断跳不跳问卷页 |
| `answer.status` | 后端把 `status_json` 解析回对象 |
| `answer.interest` | 后端把 `interest_json` 解析回数组 |

### 3.4 GET `/api/cases` —— 获取推荐案例

**作用**：按方向、年级筛选案例，返回列表。用户填完问卷后看到"和我情况相近的人怎么走的"。

**请求头**：`Authorization: Bearer <token>`

**请求参数**（query string）：

| 参数 | 必填 | 默认 | 说明 |
|------|:----:|------|------|
| `direction` | ❌ | 用户问卷里的方向 | 方向，如 `考研` |
| `grade` | ❌ | 用户问卷里的年级 | 年级，如 `大三` |
| `limit` | ❌ | `3` | 返回条数 |

> **默认值取自用户自己的问卷**。前端可以不传参数，后端自动用该用户的问卷结果去匹配；
> 前端也可以传（比如首页想手动切方向看别的案例）。

**请求示例**：

```
GET /api/cases?direction=考研&grade=大三&limit=3
```

**返回**：

```json
{
  "code": 0,
  "msg": "成功",
  "data": {
    "total": 5,
    "list": [
      {
        "id": 1,
        "title": "双非计算机大三考研上岸 211",
        "direction": "考研",
        "school_level": "普通一本",
        "major_type": "理工类",
        "grade": "大三",
        "score_level": "前30%",
        "summary": "大三上定校，暑假强化，12月上岸",
        "result": "已上岸某 211 计算机"
      }
    ],
    "relaxed": false
  }
}
```

**列表页字段**：**不返回 `experience` 和步骤**（那是详情页的事），保持列表轻量。

**返回字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `total` | int | 匹配到的**总数**（截断成 `limit` 条之前的数量） |
| `list` | array | 案例列表，字段同 `cases` 表（不含 `experience`） |
| `relaxed` | bool | **`true` = 这批案例跟用户选的方向不完全一致**，前端要提示"为你推荐了相近方向的案例" |

**匹配逻辑（三层兜底，后端已实现）**：

```
第 1 层：direction + grade 都精确匹配          → relaxed = false
第 2 层：只匹配 direction，年级放宽（同年级排前面） → relaxed = false
第 3 层：direction 也匹配不到（如"还没想好"）    → 给全表通用案例，relaxed = true
```

**排序规则**：每一层内部，**同年级的案例排在前面**（`ORDER BY (grade = ?) DESC, id`），
让用户先看到处境最接近的。

> ⚠️ **三层兜底都必要**。案例库目前是 6 个方向各 3 条，但如果用户选了
> 「**还没想好**」（问卷里确实有这个选项，且案例库**故意没有**对应案例），
> 第 1、2 层都会空，必须靠第 3 层兜住，否则页面白屏。

**「还没想好」怎么处理**：这是"用户还没定方向"的正常状态，不是数据缺失。
后端让它走第 3 层，返回通用案例 + `relaxed=true`，前端文案改为
「先看看大家的选择，再决定自己的路」。

**没有问卷又没传参数时**：返回 `{ "code": 1005, "msg": "请先完成问卷" }`，前端引导去填问卷。

### 3.5 GET `/api/cases/<id>` —— 案例详情

**作用**：点开一条案例，看完整的时间线、关键节点、经验教训。

**请求头**：`Authorization: Bearer <token>`

**路径参数**：`id` = 案例 ID

**请求示例**：`GET /api/cases/3`

**返回**：

```json
{
  "code": 0,
  "msg": "成功",
  "data": {
    "id": 3,
    "title": "双非计算机大三考研上岸 211",
    "direction": "考研",
    "school_level": "普通一本",
    "major_type": "理工类",
    "grade": "大三",
    "score_level": "前30%",
    "summary": "大三上定校，暑假强化，12月上岸",
    "experience": "数学开始太晚，暑假才意识到进度落后，建议大家大三上就开始一轮",
    "result": "已上岸某 211 计算机",
    "steps": [
      { "phase": "大三上", "content": "确定目标院校，开始数学一轮复习", "is_key": 0, "order_no": 1 },
      { "phase": "大三下", "content": "英语单词 + 专业课教材过一遍", "is_key": 0, "order_no": 2 },
      { "phase": "暑假",   "content": "强化阶段，数学刷 1000 题",       "is_key": 0, "order_no": 3 },
      { "phase": "9月",    "content": "预报名（关键节点，别错过）",     "is_key": 1, "order_no": 4 },
      { "phase": "10月",   "content": "正式报名",                       "is_key": 1, "order_no": 5 },
      { "phase": "12月",   "content": "参加初试",                       "is_key": 1, "order_no": 6 }
    ]
  }
}
```

**关键说明**：

- `steps` 是数组，**按 `order_no` 升序**排列
- `is_key = 1` 的步骤是**关键节点**（报名、考试这类不能错过的日期），前端要用醒目的颜色标出来
- `steps` 来自 `case_steps` 表，一次查询 join 出来，不要循环查数据库（N+1 问题）

**案例不存在**：`{ "code": 1001, "msg": "案例不存在" }`（沿用"参数不对"的码）

### 3.6 POST `/api/chat` —— 向大模型提问

**作用**：用户基于**自己的问卷结果**问问题，模型带着用户画像回答。

**请求头**：`Authorization: Bearer <token>`

**请求体**：

```json
{ "question": "我数学基础差，现在开始考研来得及吗？" }
```

**成功返回**：

```json
{
  "code": 0,
  "msg": "成功",
  "data": {
    "answer": "以你大三、理工类、普通一本的背景，现在开始来得及，但要抓三件事：……",
    "tokens_used": 328
  }
}
```

**失败情况**：

| 情况 | 返回 |
|------|------|
| 未登录 | `{ "code": 401, "msg": "请先登录" }` |
| `question` 为空 | `{ "code": 1001, "msg": "请输入你的问题" }` |
| **没填过问卷** | `{ "code": 1005, "msg": "请先完成问卷，我才能针对你的情况回答" }` |
| 今日提问超过上限 | `{ "code": 1007, "msg": "今日提问次数已用完，明天再来" }` |
| 模型调用失败 / 超时 | `{ "code": 2001, "msg": "AI 暂时不可用，请稍后再试" }` |

**后端实现要点（★ 这是第三层最关键的地方）**：

**不能只是把用户的问题转发给模型**。要把用户问卷结果拼进 System Prompt：

```python
ans = Answers.query.filter_by(user_id=uid).first()
if ans is None:
    return fail(1005, "请先完成问卷，我才能针对你的情况回答")

status = json.loads(ans.status_json or "{}")
interest = json.loads(ans.interest_json or "[]")

system_prompt = f"""
你是一个大学生未来规划助手。用户信息如下：
- 年级：{ans.grade}
- 专业：{status.get('major_type')}
- 学校：{status.get('school_level')}
- 成绩：{status.get('score')}
- 方向：{ans.direction}
- 想搞清楚：{'、'.join(interest)}

请基于以上信息，给出具体、可执行的建议。不要给"要努力学习"这类空话。
"""
```

**这样"问同一句话、不同用户答案不同"，才是老师要的"根据用户需求对答如流"。**

**成本控制（老师强调过两遍，务必照做）**：

| 措施 | 实现 |
|------|------|
| key 不进仓库 | 写在 `backend/.env`，已在 `.gitignore` |
| 每日次数上限 | 查 `chat_logs` 今天该用户的记录数，超过 N（如 20）返回 1007 |
| 记录用量 | 每次调用后往 `chat_logs` 插一条（含 `tokens_used`） |
| 模型异常兜底 | 调用超时/报错 → 返回 2001，**不要把异常堆栈返回给前端** |

**每次调用后必须落库**：

```python
db.session.add(ChatLog(
    user_id=uid,
    question=question,
    answer=answer_text,
    tokens_used=tokens,
))
db.session.commit()
```

### 3.6.1 B 的实现说明（2026-10-08 补充）

上面 3.6 节是 C 定的契约，以下是 B 实现时**额外加的字段和接口**，前端可以按需使用：

#### `data` 里多返回了 2 个字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `mock` | bool | **骨架阶段固定为 `true`**，表示这次回答没走真实模型。接上真模型后改成 `false`，前端不用改代码，只用它决定要不要在页脚显示"演示模式" |
| `system_prompt` | string | 实际拼给大模型的系统提示词。**返回出来是为了让老师和你们能直接验证"问卷有没有真的带进去"** —— 不同用户发同一个问题，如果这段文字不一样，就说明拼对了。接上真模型后可以决定是否继续返回 |

#### 额外加了 `GET /api/chat/logs`（文档未要求）

| 项 | 值 |
|----|-----|
| 作用 | 查自己的提问记录（倒序），并返回今日额度 |
| 请求头 | `Authorization: Bearer <token>` |
| 参数 | `limit`：默认 20，上限 50（非法值自动回退到默认） |
| 返回 | `{list, total, daily_limit, remaining}` |
| `list` 字段 | `id` / `question` / `answer` / `tokens_used` / `created_at`（**不含 user_id**，不泄露别人的信息） |

**为什么加它**：文档只要求 POST，但 `chat_logs` 落了库却查不出来，等于没法验证"有没有真的记进去"，前端也没法做历史列表。另外 `remaining` 能让前端提前禁用提问按钮，而不是让用户点了 20 次才被告知用完了。

#### 两个实现细节（供 C 参考）

1. **`grade` 不在 `status` 里**：它是问卷 B 组第 1 题，在 `answers.grade` 上单独存。拼 prompt 时要注意取的是 `ans.grade` 而不是 `status.get('grade')`。
2. **校验优先级**：401 → **1005（未填问卷）** → 1001（question 格式）→ 1007（次数上限）。1005 排在 1001 前面，因为没填问卷时最该做的是引导用户去填，而不是纠正他的输入格式。

### 3.6.2 ⚠️ 每日额度必须加数据库行锁（2026-10-09 踩过，务必照做）

这一条是实现 `/api/chat` 时最容易踩、也最难自己发现的坑，记下来给后面接手的同学。

**问题**：如果按字面写「先 `count()` 一下今天的条数，超过 20 就返回 1007；没超就 `insert()`」，
这两步之间有时间差，**并发请求会互相穿插**。

**实测（2026-10-09）**：同一账号同时发 25 个请求，结果是

```
25 个请求全部返回 code:0「提问成功」
但 chat_logs 里只有 20 条
```

也就是说**有 5 次白问了** —— 用户界面上看到的是"成功"，但刷新历史记录找不到这次回答，
额度也被白白占掉。骨架阶段只是难看；**接上真实模型后，这 5 次就是真金白银的浪费**。

**正确做法**（见 `backend/app/routes/chat.py` 的 `_reserve_quota()`），三个要点：

| # | 做法 | 原因 |
|---|------|------|
| 1 | **锁 `users` 表那一行**（`SELECT ... FOR UPDATE`），不要锁 `chat_logs` | MySQL 行锁只能锁**已存在的行**。`chat_logs` 里的行是各自请求刚插的、彼此看不见，锁它没用；而 `users` 里这个用户一定存在 |
| 2 | 先插一条 **`answer=NULL` 的占位记录**再返回对象给调用方 | 后面的模型调用若抛异常，这一行能整体回滚，用户额度不被扣（"没得到答案就不该扣费"）。调用方拿对象引用直接改，**不要回头去"找最新一条 answer=None 的记录"**（同用户并发时会取错行） |
| 3 | 只读接口（如 `GET /chat/logs` 显示剩余额度）**不需要加锁** | 差一两条在展示场景下无所谓；真正把关额度的只有 `_reserve_quota()` |

**修好后的验证结果**：

```
并发 25 次 → 20 个 code:0（成功）+ 5 个 code:1007（超额）
chat_logs 行数：恰好 20
```

**自查方法**（可复用）：同一账号并发发 N 个请求（N > 上限），然后数 `chat_logs` 里该用户的行数，
应该**恰好等于上限**；返回值里成功的和 `1007` 的数量加起来应该等于 N。

## 六、接口自测方法（B 写完自己先测）

不用装 Postman，用 VS Code 的 REST Client 或者直接用 curl：

```bash
# 1. 先登录拿 token（用第一阶段接口）
curl -X POST http://localhost:5000/api/login \
  -H "Content-Type: application/json" \
  -d '{"username":"testuser","password":"123456"}'
# 记下返回的 data.token

# 2. 测问卷题目（不用 token）
curl http://localhost:5000/api/questions

# 3. 测提交问卷（换成你的 token）
curl -X POST http://localhost:5000/api/answers \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer 你的token" \
  -d '{"direction":"考研","grade":"大三","status":{"major_type":"理工类"},"interest":["具体怎么准备"],"extra_note":""}'

# 4. 测查案例
curl "http://localhost:5000/api/cases?direction=考研&grade=大三" \
  -H "Authorization: Bearer 你的token"
```

**测试要点**：

- 不带 token 调 `/api/answers` → 应该返回 401
- `direction` 传个乱值（比如 `"abc"`）→ 应该返回 1006
- 提交两次问卷 → 数据库里应该只有一条记录（覆盖，不是新增）
