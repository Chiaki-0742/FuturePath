# FuturePath 第二阶段功能设计

**版本**：v1.0
**日期**：2026-09-30
**阶段**：第二周起（国庆期间启动）

---

## 一、这一阶段要做什么

第一阶段做完了**用户系统**（注册 / 登录 / 改资料）。但用户登录进来之后无事可做——
系统只有"你是谁"，没有"你该往哪走"。

这一阶段就是补上这个缺口。核心思路是**三层递进**：

```
第一层：问卷收集   →  先搞清楚用户是什么情况
   ↓
第二层：案例参考   →  给用户看"别人是怎么走的"
   ↓
第三层：大模型对话 →  用户能问"我这个情况该怎么办"
```

**为什么是这个顺序**（重要，别打乱）：

| 层 | 为什么在前 |
|---|---|
| 问卷 | 是后面两层的数据源。不知道用户是考研还是就业、大几、成绩如何，案例和大模型都答不准 |
| 案例 | 问卷告诉系统"用户想考研"，案例回答"考研要做哪些事"。用户拿到能直接抄的答案，不依赖大模型 |
| 大模型 | 前两层解决"通用问题"，大模型解决"我这个特殊情况"。它需要前两层的结果作为上下文 |

**关键取舍**：前两层**不需要大模型**，纯靠数据库 + 前端就能做完全。
这意味着**国庆期间可以立刻开工，不用等 API 申请、不用花钱**。
大模型放最后，是锦上添花，不是地基。

## 二、第一层：问卷收集

### 2.1 什么时候填

用户**注册成功后第一次进入首页**时，引导填写问卷。

- 没填过的用户 → 自动跳转到问卷页
- 填过的用户 → 正常进首页（可以在个人中心再次修改）

### 2.2 问卷内容（三组）

**A 组：未来方向**（单选主方向，可多选备选）

| 选项 | 说明 |
|---|---|
| 考研 | 继续读研深造 |
| 就业 | 毕业后直接工作 |
| 考公 / 考编 | 公务员、事业单位 |
| 留学 | 出国申请 |
| 创业 | 自己做事 |
| 还没想好 | 需要系统帮判断 |

**B 组：当前现状**

| 问题 | 类型 | 选项 / 说明 |
|---|---|---|
| 当前年级 | 单选 | 大一 / 大二 / 大三 / 大四 / 研究生 |
| 所在专业 | 单选 | 理工类 / 文史类 / 经管类 / 艺术类 / 医学类 / 其他 |
| 学校层次 | 单选 | 985/211 / 普通一本 / 二本 / 专科 |
| 成绩水平 | 单选 | 专业前 10% / 前 30% / 中等 / 偏下 |
| 英语水平 | 单选 | 已过六级 / 已过四级 / 未过四级 |
| 已有经历（多选） | 多选 | 实习 / 科研 / 竞赛获奖 / 学生工作 / 项目经历 / 都没有 |

**C 组：你最想知道什么**

| 问题 | 类型 | 选项 |
|---|---|---|
| 最想搞清楚的问题 | 多选（最多 3 个） | 该选哪条路 / 每条路的利弊 / 具体怎么准备 / 时间节点怎么安排 / 需要具备什么能力 / 怎么弥补短板 |
| 补充说明 | 填空 | 选填，用户自由描述 |

**设计原则**：
- **一共不超过 10 题**，控制在 2 分钟内填完。题目太多用户会中途放弃
- 大部分是**选择题**，只有最后一个是填空。降低填写成本
- 选项要**具体**，不要"成绩好 / 一般 / 差"，要"专业前 10% / 前 30% / 中等 / 偏下"

### 2.3 数据怎么存

新增两张表（详见第四节）：

| 表 | 用途 |
|---|---|
| `questions` | 题库（所有题目存在这里，不写死在代码里） |
| `answers` | 用户答案（一条记录 = 一个用户的一份问卷） |

**为什么题库要独立成表**：以后加题、改题、调整选项，只改数据库，不用改代码重新部署。
这是数据库设计的基本功，也是你这个角色的核心贡献。

### 2.4 界面长什么样

单页分段式，三组题目分三屏，底部一个"下一步"按钮：

```
┌────────────────────────────┐
│  第 1 步 / 共 3 步          │
│  ████░░░░░░░░░░  33%       │
├────────────────────────────┤
│                            │
│  你毕业后想去哪？            │
│                            │
│  ○ 考研    ○ 就业           │
│  ○ 考公    ○ 留学           │
│  ○ 创业    ○ 还没想好       │
│                            │
│              [ 下一步 ]     │
└────────────────────────────┘
```

## 三、第二层：案例参考

### 3.1 是什么

系统内置一批**真实感的人物案例**。用户选完问卷后，看到和自己情况相近的人是怎么走过来的。

> 例：**小王，双非一本，计算机专业，大三，成绩中等，选择考研**
> - 大三上：确定目标院校，开始数学一轮复习
> - 大三下：英语单词 + 专业课教材过一遍
> - 暑假：强化阶段，数学刷 1000 题
> - 大四上：政治冲刺，真题模拟，12 月考试
> - **关键节点**：9 月预报名、10 月正式报名、12 月考试
> - **踩过的坑**：数学开始太晚，暑假才意识到进度落后

### 3.2 案例怎么组织

一条案例包含：

| 部分 | 内容 |
|---|---|
| 基本画像 | 学校层次、专业、年级、成绩、方向 |
| 时间线 | 按学期/月份列出每个阶段做了什么 |
| 关键节点 | 报名时间、考试时间、重要截止日期 |
| 经验教训 | 踩过的坑、后悔的事 |
| 结果 | 最终去了哪（增加可信度） |

### 3.3 推荐逻辑（第一版用简单规则）

用户填完问卷 → 按**方向 + 年级**匹配案例：

```
用户选了「考研」+「大三」
   ↓
筛选：cases 表里 direction='考研' 的案例
   ↓
再按年级、成绩做二次排序
   ↓
展示前 3 条
```

**第一版不搞复杂算法**，就是"方向对上 + 年级相近"就给。够用，而且快。

后面可以升级为：专业对上 → 成绩相近 → 更有针对性。

### 3.4 案例从哪来

三个来源，按优先级：

| 来源 | 做法 | 说明 |
|---|---|---|
| **自己编** | 按常见路径写 10-15 条标准案例 | 最快，国庆就能做。**先做这个** |
| 网上整理 | 从知乎/小红书扒真实经验贴，改写成统一格式 | 内容更真，但要花时间整理 |
| 学长学姐访谈 | 找身边真实的人聊 | 最有说服力，后期做 |

**建议先做 10 条**，覆盖 5 个方向 × 2 个主要年级。够演示，够用。

### 3.5 数据怎么存

新增两张表：

| 表 | 用途 |
|---|---|
| `cases` | 案例主表（画像 + 时间线 + 经验） |
| `case_steps` | 案例的步骤明细（一条案例对应多条步骤） |

## 四、第三层：大模型对话

### 4.1 目标

用户能基于**自己的问卷结果**问问题：

> "我双非大三想考 211 计算机，数学基础差，现在开始来得及吗？"

### 4.2 关键设计：怎么让回答"懂我"

**绝对不能只是转发用户的问题**。要在请求里带上用户的问卷结果作为上下文：

```
系统提示词（System Prompt）：
  你是一个大学生规划助手。用户信息如下：
  - 年级：大三
  - 专业：理工类
  - 学校：普通一本
  - 成绩：前 30%
  - 方向：考研
  - 想搞清楚：具体怎么准备、时间节点

  请基于以上信息，给出具体、可执行的建议。
  不要给"要努力学习"这类空话。

用户问题：
  数学基础差，现在开始来得及吗？
```

**这样回答才有用**。否则和直接问 ChatGPT 没区别——老师要的"根据用户需求来对答如流"，关键就在这个"根据"。

### 4.3 成本控制（老师特意强调了两遍）

| 措施 | 做法 |
|---|---|
| **key 不进仓库** | 写在 `backend/.env` 里，已在 `.gitignore` 中 |
| **设置用量上限** | 在模型平台后台设置每月消费上限（如 50 元） |
| **限制提问频率** | 每个用户每天最多 N 次（如 20 次），防止刷 |
| **记录用量** | 建 `chat_logs` 表，记录每次调用，能查能控 |
| **先选便宜的模型** | DeepSeek 等国产模型价格远低于国外，够用 |
| **答案可以缓存** | 相同问题直接返回上次答案 |

### 4.4 放在最后做的理由

| 理由 | 说明 |
|---|---|
| 有前置依赖 | 需要问卷数据作为上下文 |
| 有外部依赖 | 要申请 API key、要审批、要充钱 |
| 有不确定性 | 模型输出不稳定，需要反复调提示词 |
| **不是地基** | 问卷和案例做完，App 已经可用了 |

## 五、数据库设计（你负责的核心部分）

### 5.1 新增表清单

| 表名 | 用途 | 归属层 |
|---|---|---|
| `questions` | 问卷题库 | 第一层 |
| `answers` | 用户问卷答案 | 第一层 |
| `cases` | 案例主表 | 第二层 |
| `case_steps` | 案例步骤明细 | 第二层 |
| `chat_logs` | 大模型对话记录 | 第三层 |

### 5.2 表结构

**`questions` —— 问卷题库**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INT PK AUTO_INCREMENT | 主键 |
| group_name | VARCHAR(32) NOT NULL | 分组：direction / status / interest |
| content | VARCHAR(255) NOT NULL | 题干 |
| q_type | VARCHAR(16) NOT NULL | 类型：single / multi / text |
| options | TEXT NOT NULL | 选项，JSON 数组格式 |
| order_no | INT NOT NULL | 排序号 |
| created_at | DATETIME | 创建时间 |

**`answers` —— 用户答案**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INT PK AUTO_INCREMENT | 主键 |
| user_id | INT NOT NULL | 外键 → users.id |
| direction | VARCHAR(32) NOT NULL | 主方向（考研/就业…） |
| grade | VARCHAR(16) | 年级（冗余，方便查询） |
| status_json | TEXT | B 组现状答案，JSON |
| interest_json | TEXT | C 组想了解什么，JSON |
| extra_note | TEXT | 用户补充说明 |
| created_at | DATETIME | 填写时间 |

> `user_id` 加 **UNIQUE 索引**：一个用户只有一份问卷，重复提交则覆盖。

**`cases` —— 案例主表**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INT PK AUTO_INCREMENT | 主键 |
| title | VARCHAR(128) NOT NULL | 案例标题，如"双非计算机大三考研上岸 211" |
| direction | VARCHAR(32) NOT NULL | 方向 |
| school_level | VARCHAR(32) | 学校层次 |
| major_type | VARCHAR(32) | 专业类型 |
| grade | VARCHAR(16) | 年级 |
| score_level | VARCHAR(32) | 成绩水平 |
| summary | TEXT | 一句话概述 |
| experience | TEXT | 经验教训、踩过的坑 |
| result | VARCHAR(255) | 最终结果 |
| created_at | DATETIME | 创建时间 |

**`case_steps` —— 案例步骤**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INT PK AUTO_INCREMENT | 主键 |
| case_id | INT NOT NULL | 外键 → cases.id |
| phase | VARCHAR(64) NOT NULL | 阶段，如"大三上" |
| content | TEXT NOT NULL | 该阶段做了什么 |
| is_key | TINYINT | 是否关键节点（0/1） |
| order_no | INT NOT NULL | 排序号 |

**`chat_logs` —— 对话记录**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INT PK AUTO_INCREMENT | 主键 |
| user_id | INT NOT NULL | 外键 → users.id |
| question | TEXT NOT NULL | 用户问的 |
| answer | TEXT | 模型答的 |
| tokens_used | INT | 消耗的 token 数（用于控成本） |
| created_at | DATETIME | 时间 |

### 5.3 表关系图

```
users (已有)
  │
  ├──1:1── answers      （一份问卷）
  └──1:N── chat_logs    （多条对话）

cases
  │
  └──1:N── case_steps   （多条步骤）

questions （独立题库，不被外键引用）
```

### 5.4 设计原则（写代码时注意）

1. **所有业务表带 `user_id`** —— 数据隔离，A 查不到 B 的数据
2. **外键 + 索引** —— `user_id`、`case_id` 都要建索引，查询快
3. **JSON 存灵活数据** —— `options`、`status_json` 用 TEXT 存 JSON，结构变了不用改表
4. **`init.sql` 与后端模型必须同步** —— 改一处就要改另一处（这是第一周踩过的坑）
5. **给案例准备种子数据** —— `init.sql` 里直接 INSERT 10 条案例，别人 clone 完就有内容看

## 六、接口设计

### 6.1 新增接口清单

| 接口 | 方法 | 作用 | 归属 |
|---|---|---|---|
| `/api/questions` | GET | 获取问卷题目 | 第一层 |
| `/api/answers` | POST | 提交问卷答案 | 第一层 |
| `/api/answers` | GET | 查询我的问卷结果 | 第一层 |
| `/api/cases` | GET | 获取推荐案例（按方向/年级筛选） | 第二层 |
| `/api/cases/<id>` | GET | 案例详情（含步骤） | 第二层 |
| `/api/chat` | POST | 向大模型提问 | 第三层 |

### 6.2 接口约定（继承第一周规范）

统一返回格式：

```json
{ "code": 0, "msg": "成功", "data": {} }
```

新增错误码（沿用 1001-1004 之后）：

| code | 含义 |
|---|---|
| 1005 | 问卷未填写 |
| 1006 | 问卷格式不对 |
| 1007 | 提问太频繁（超过每日限制） |
| 2001 | 大模型服务异常 |

### 6.3 关键接口示例

**POST /api/answers** —— 提交问卷

```
请求头：Authorization: Bearer <token>
请求体：
{
  "direction": "考研",
  "grade": "大三",
  "status": { "major_type": "理工类", "school_level": "普通一本", "score": "前30%" },
  "interest": ["具体怎么准备", "时间节点怎么安排"],
  "extra_note": "数学基础比较差"
}

返回：
{ "code": 0, "msg": "提交成功", "data": { "id": 1 } }
```

**GET /api/cases?direction=考研&grade=大三**

```
返回：
{
  "code": 0,
  "data": {
    "list": [
      {
        "id": 3,
        "title": "双非计算机大三考研上岸 211",
        "direction": "考研",
        "grade": "大三",
        "summary": "大三上定校，暑假强化，12月上岸",
        "result": "已上岸某 211 计算机"
      }
    ]
  }
}
```

## 七、开发顺序

**必须按这个顺序做，后一层依赖前一层。**

| 步骤 | 内容 | 依赖 |
|---|---|---|
| 1 | 设计并建 5 张新表（`init.sql`） | 无 |
| 2 | 导入题库种子数据 + 10 条案例数据 | 步骤 1 |
| 3 | 后端：问卷相关 3 个接口 | 步骤 1 |
| 4 | 前端：问卷页面（三屏） | 步骤 3 |
| 5 | 后端：案例相关 2 个接口 | 步骤 2 |
| 6 | 前端：案例列表页 + 详情页 | 步骤 5 |
| 7 | 联调：填问卷 → 看案例 | 步骤 4、6 |
| 8 | 后端：接入大模型接口 | 步骤 3 |
| 9 | 前端：对话页面 | 步骤 8 |
| 10 | 切 MySQL + 部署上线 | 全部 |

**第 1-7 步不需要大模型，国庆期间就能全部做完。**

## 八、验收标准

| 环节 | 怎么算通过 |
|---|---|
| 问卷 | 新用户注册后被引导填问卷，2 分钟内填完，数据落库 |
| 案例 | 填完问卷 → 看到和自己方向匹配的案例 → 能点开看完整步骤 |
| 大模型 | 提问时回答能体现"知道我的情况"（问同一问题，不同用户答案不同） |
| 整体 | 新用户从注册到看到案例，全程无需看文档就会用 |
